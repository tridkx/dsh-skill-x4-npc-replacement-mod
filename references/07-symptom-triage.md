# §11 症状 → 根因 → 修法（实机反馈决策树）

> 每条都注明"怎么量"，因为**猜错方向的成本远高于量一次**。

## §11.1 动作时四肢朝反方向弯、手指被拉长

**根因**：顶点在绑定姿态下离它的主导骨太远（本例手 42 cm），动画一播就被甩错方向。

**先量**：

```
每顶点到主导骨线段的平均距离，按部位分组；与 vanilla 同口径比
vanilla 手指 1.11 / 手 5.34；本例出问题时有 23.9 / 17.3
```

**别走的路**：用"绕肩旋转手臂顶点"之类的**局部 hack** 去救。
本例在这条路上卡了很久（误差 20.6 → 21.7）。局部 hack 治不了"整条链的比例差"。

**修法**：见 `02-retargeting.md`
1. 先确认坐标映射符号（`01-coordinate-frames.md`）—— 符号错了残差也会堆在四肢
2. 再做**逐骨绑定姿态转移**
3. 骨轴用**主链第一个子骨**（骨盆尤其容易错）
4. 折叠骨**锚定**到最近的直接骨

## §11.2 脸整个消失 / 衣裤鞋透明、能看穿到对面内壳

**根因**：三角形绕序翻转（法线朝内），引擎剔除正面。

**为什么迷惑**：所有基于顶点位置的检查全部正常（指标、包围盒、骨骼叠加）。

**先量**：`check_normals.py` → 比例 < 0.5 即确诊。

**修法**：建网格时反转三角形 `(a,b,c) → (c,b,a)`；同时确认坐标映射用的是
**物理正确**的那一支（`(x, z, y)`，det = −1）。

> 相关的反向错误：如果映射写成 `(x, −z, y)`（det = +1），绕序正常但**前后镜像**，
> 残差堆在四肢而躯干正常 —— 见 §11.1。

## §11.3 腰部有莫名其妙的横向色带 / 衣服颜色与原版对不上

**根因**：源数据里"只有 shader 参数、没有 albedo"的材质（缝线/底座类）
拿到了手工填的深色占位，而且缺 smoothness 贴图时导出器写死 `Smoothness = 0.5`
（本体是 0.08 哑光）→ 深色 + 反光。

**先量**：用材质染色渲染（`color_type='MATERIAL'` + `material.diffuse_color`）
确认那条带属于哪个材质；再查该材质在源数据里有没有 albedo。

**修法**：见 `04-materials-and-textures.md` §7.3
按 UV 采样主材质求均色 + 继承主材质粗糙度。

> **注意**：这类材质常常是**成片几何**（本例夹克缝线 3799 顶点、金属件 7776），
> 不是细线。可以先用"提高减面比例"验证 —— 如果一带被减面削到看不见，
> 问题就被掩盖了，等你把比例提回来它又会冒出来。

## §11.3b 身上出现亮粉色/洋红的小片

**两种完全不同的原因，先分清**：

| 现象 | 原因 | 修法 |
|---|---|---|
| 某块几何**整片发白/粉**，且它是深色部件 | **BC3 块顺序写反**（自研编码器） | 见 `04-materials-and-textures.md` §7.4.0 —— DXT5 是 `[alpha][color]` |
| 小块**刺眼的洋红**（255,0,255） | 游戏**找不到/不接受**那张贴图 | 见 §7.4.1 —— 特别是 16×16 的纯色占位图会被拒 |

**定位手法**（本例绕了几圈才找到，按这个顺序最快）：

1. **按用户指的坐标放大实机截图** —— 不要自己猜位置。
2. **确认它属于哪个部件**：形状像带扣就是挎带、像手指就是手 …… 用户往往一眼能认出来。
3. **量那张贴图的源与转换结果**：

   ```
   源   ch01_6004_sling_albd.png      RGB 均值 (40, 36, 34)
   转换 rose_sling_mat_diff.dds       RGB 均值 (235, 218, 234)   ← 明显不对
   ```

   源与转换结果的均值差这么远，就是编码/转换环节的问题，不用再怀疑几何或 UV。
4. **确认它走哪条编码分支**：带 alpha 的材质走 BC3 —— 这是最容易被忽略的分支。

## §11.4 虎口/指间裂开，像平白少了一块皮

**根因**：源角色手指**并拢**、X4 手指骨**张开**；逐骨对齐 = 把手掰开，
而指间的皮没有自己的几何，只是两侧皮肤的过渡 → 撕开。

**修法**：见 `02-retargeting.md` §4.5 —— **手指权重整体绑到手掌骨**。

**不要取的中间态**：半量混合（各 50%）会让**五根手指各自扭曲**，比两端都差。
要么全跟骨骼、要么全跟手掌。

## §11.5 脚跟悬空、只有前掌着地

**先量**：把脚部顶点按前后分带，看各带的最低 z。

```
             脚跟    足弓    前掌    脚趾
vanilla     -0.15   -0.25   -0.32    1.10
出问题       5.43    3.23   -0.48   -0.59
```

**根因**：不是旋转，是**位移差** —— `Toe0` 的目标比源骨低 3.1 cm，`Foot` 高 2.0 cm，
逐骨各走各的把脚撬斜。

**修法**：见 `02-retargeting.md` §4.6 —— 整只脚共用踝关节位移 + 地面**双向**对齐。

> 只做"去掉脚骨旋转"只能恢复约 1/4 的偏差，别停在那里。

## §11.6 手指上有一圈圈横纹 / 指根深色斑块

**根因**：切线跟着 UV 走；对**手**做减面会重写手指 UV → 切线空间错乱 →
法线贴图渲染成环纹。

**为什么之前看不到**：workbench 预览**不显示法线贴图**。必须用 **EEVEE** 复现。

**修法**：手部**完全不减面**（`ratio = 1.0`），并跳过手部的权重平滑。

## §11.7 脸上/身上有明显面片，显得粗糙

**先量**：导入成品 `.xac`，量 `|顶点法线 − 面法线|`。

```
0.000  = 平面着色（错）
0.4 左右 = 平滑（对）
```

**根因**：两段式管线里**只有 stage1 设了平滑**，stage2 用 `from_pydata`
重建网格时默认回到平面着色，而导出器读 `loop.normal`。

**修法**：两个阶段都设 `poly.use_smooth = True`。
**顺带收益**：消掉法线接缝，导出顶点约 −70%，可以把预算花到面数上。

## §11.8 空间站频闪 / 地图卡死 / 地图彩色斑块

**根因**：资产顶点数远超 vanilla（NPC 是实例化渲染，地图要画全部对象）。

**量级**：vanilla ~5k/资产；本例 9× 稳定、15.5× **频闪复发**、终版 6.3× 稳定。

**修法**：降 `DECIMATE_RATIO`；**优先提升"法线"而不是"减面"**
（见 §11.7，平滑法线本身就是一大笔预算）。

> 注意口径：导出器的顶点计数**含 UV/法线接缝**，比较时要用导出后的数字。

## §11.9 眼球不见 / 偶尔错位不跟头

**两个独立原因**：

1. **几何用错了**：源资产里可能有一个"位置偏低的眼球拷贝"。
   先量源数据各子网格的高度分布，用**与眼睑对齐**的那一个。
2. **look-at 甩飞**：X4 用 look-at 驱动 `left/right_eye_dummy`，
   而源眼球几何离这两根骨很远 → 视线一转就飞出去。
   **修法：这两根骨上的权重改挂 `Bip01 Head`**（稳定优先，放弃眼球随视线转）。

## §11.10 头缩在衣领里

**先量**：眼球（或脸顶）与夹克领口的高度差。

```
源数据 7.5 cm    vanilla 9.9 cm    出问题 0.6 cm
```

**根因**：X4 的 `Head` 只比 `Neck` 高 7.8 cm，源的高 13.7 cm。各自对齐 →
头被拽下、领口被推上。

**修法**：见 `02-retargeting.md` §4.8 —— **头颈共用一份位移**（取两者平均）。

## §11.11 改了 XML 但游戏里没变化

**先查**（按可能性排序）：

1. `sel=` 的 XPath 写错 → 游戏**静默忽略**。用自检脚本的"XPath 能命中"一条排除。
2. `.cat/.dat` 没重新打包，或没复制到 `extensions/<mod_id>/`。
3. 用的是 `<add>`（追加，1/N 概率）而不是 `<replace>`（整池替换）——
   遇到原版外观是正常的。
4. 游戏没重启 / 扩展没启用。
5. **NPC 外观在实例化时决定**，已在场景里的 NPC 不会立刻变。

## §11.12 改了管线但产物没变

**先查** `05-export-and-packaging.md` §9.3 的三个陷阱（目录已存在 / 删对象无效 /
空槽位不可表达）。这类"静默保留旧产物"的行为最容易浪费一整轮调试。

## §11.13 贴图整体上下颠倒 / 花纹错位（UV 的 v 轴）

**症状**：整张贴图在模型上**上下翻过来**（眼睛长到额头上、衣服图案倒置、
脸的上半部采样到下半部的图），而几何、骨骼、法线、材质全部正常。

**根因**：UV 的 v 有三层约定，中间**差两次翻转**：

```
PMX 的 v        0 在图像顶端（向下）
Blender 的 v    0 在图像底端（向上）        ← 与 PMX 本来就差一次 1−v
导出器 addon.py:855   v_x4      = 1 − v_blender
导入器 addon.py:531   v_blender = 1 − v_x4      （对称，所以 v_x4 与 Blender 反号）
```

目标是 X4 里的 v **等于** `v_pmx`（两者都向下）。导出器会翻一次，
所以 **Blender 里必须存 `1 − v_pmx`**。stage1 若原样传递 `v_pmx`，
X4 拿到的就是 `1 − v_pmx` —— 整张贴图上下颠倒。

**为什么前两个项目没暴露**：艾梅莉埃的代码注释写着
"pass through unchanged: the exporter applies `1 - uv.y` itself"。
那句话只对了一半 —— 它翻的是 **Blender 的 v**，
而 Blender 的 v 与 PMX 的 v 本来就差一次。

**验证链**（可复现，数字可对照）：

```
源 PMX skin              v [0.0615, 0.9263]      ← 目标：xac 里的 v 也是这个值
期望 stage1 存 1−v        [0.0737, 0.9385]
导入 xac 回 Blender 实测   [0.0737, 0.9385]
  → v_x4 = 1 − [0.0737, 0.9385] = [0.0615, 0.9263]  ✓
```

**为什么只有实机能发现**：软渲染预览走的是**源 PMX 的 UV**（不经 Blender、
不经导出器），所以预览一直"正常"——这个错误在预览里**不可能**复现。
判据只能取"导入成品 xac、逐网格 dump v 范围、与 `1 − v_pmx` 比"。

**修法**：stage1 建网格时写入 `1 − v_pmx`（u 不变）。
**不要**去改导出器：它与导入器是对称的一对，改它会同时破坏读取回程。

## §11.14 衣服上与皮肤同位置的地方有一片片闪烁的黑斑

**症状**：衣服/配饰与皮肤（或两层衣服）重叠处出现**一片片随视角闪烁的深色斑块**；
截图静止时看不出，摄像机一动就跳。

**根因**：两层几何**位置重合 → 深度相同**，深度缓冲无法稳定判定谁在前，
逐像素在"皮肤"和"衣服"之间跳。这不是着色问题，改材质、调颜色都没有用。

**先量**：`diag_overlays.py` —— 对每一对部件做 KD-tree 最近邻（两个方向都算），
统计"存在对端顶点距离小于阈值"的顶点对数：

```
cloth ↔ skin      3331 对 < 4 mm，最小 0.00 mm
elem  ↔ cloth      245 对
hair  ↔ hairspec  3380 对
```

**判据**：两个硬条件 —— ① 分层对的最小距离 ≈ 0（本例最小 0.00 mm）；
② 成对顶点数不是零星几对，而是数百到数千（本例 245 – 3380）→ 确诊。

**修法**：沿**源顶点法线**把外层整体外推（法线只经旋转，不缩放、不平移）：

```
cloth  +2 mm
elem   +5 mm
hairspec  直接丢弃
```

**`hairspec` 必须丢，不是优化**：它是贴在头发上的 98% 透明的镜面叠加层，
而导出器把所有材质写成 `blendmode="NONE"`（不透明，见 §9.8）——
留着它等于用一层近黑色盖住整个头发，**金发变黑发**。

**怎么证伪**：外推后重跑 `diag_overlays.py`，同一对的最小距离应 ≥ 外推量，
实机闪烁消失。若仍有闪烁，说明还夹着第三层（本例 `elem ↔ cloth` 就是第二对）。
这是**几何层间距**问题，不要试图用 `TWOSIDED` 或调材质糊过去。

## §11.15 头发/衣服从背面看消失，或整体变成黑色

**两条不同的路，先分清**（现象相似，修法相反）：

| 现象 | 根因 | 修法 |
|---|---|---|
| 只在一个方向可见，转到背面**整片消失**（能看到内壳） | 源数据是**单面几何 + 材质标记双面**，X4 默认**剔除背面** | 材质用 `blendmode="TWOSIDED"` |
| 不论从哪看都**整体发黑**，像罩了一层 | 残留的**透明叠加层**被导出器写成不透明（§9.8 的 `blendmode="NONE"`） | 构建阶段**丢弃**该叠加层（本例 `hairspec`，见 §11.14） |

**先量（单面那一支）**：

```
本例 20/20 材质 flag bit0 置位（源侧"双面"标记）
diag_double_sided 量到 22868 面里 0 个有反向孪生面
```

即"双面"只写在材质标记里，**几何是纯单面的**；X4 不读源材质标记，
必须由 mod 侧显式声明双面。

**不要走的路：复制一份反向几何当背面层。** 第一次的修法就是这样做的
（两层各自带独立顶点，以免共享顶点把顶点法线平均到零、渲染成惨白碎条 ——
而导出的 `loop.normal` 就是这些坏法线）。两个后果：

```
两层壳位置完全相同 → 同一深度 → 实机频闪（§11.14）
顶点数翻倍：head 8195 → vanilla 4693 的 1.75×；body 20513 → 5.70×（贴着 6× 安全线）
```

**正解**：`blendmode="TWOSIDED"`。vanilla 有先例：`p1_char_spl_f_cloak_gen_01`
用的正是 `p1_character` + `TWOSIDED`。零几何成本，也不可能与自己打架。收益：

```
head 8195 → 4813（1.03×）    body 20513 → 11325（3.15×）    mod 3.0 → 2.2 MB
```

**怎么证伪**：改完必须**回读成品里的 `material_library.xml`** 确认 `TWOSIDED`
真的写进去了 —— 只改构建代码会被 §9.8 的硬编码吃掉。

## §11.16 遮罩边缘（皮肤/镂空处）有一圈深色斑点，远处更明显

**症状**：镂空边缘（发梢、睫毛、皮肤遮罩边界）出现一圈深色/发灰的斑点，
**越远越明显**，近看几乎正常。

**根因**：贴图的透明区域 RGB 是黑的，而 mip 生成是**无差别平均颜色**的：

```
本例 肌.png：88% 的像素 alpha = 0，且这些透明像素的 RGB 是纯黑
mip 第 2 级：遮罩边界上的纹素 = "肤色 + 黑"的平均 → 采样读出深灰
同时平均出来的 alpha 落在 0.5 之上 → alpha test 也剔不掉
```

实机表现就是每条遮罩边缘上的深色斑点。

**先量**：统计贴图 alpha 分布 + 透明像素的 RGB 均值。
`alpha == 0` 的像素 RGB 均值接近 0 且占比很大 → 确诊。

**修法**：在**生成 mip 之前**把不透明像素的颜色向透明区扩张
（形态学膨胀，本例 12 圈），**alpha 保持原样** ——
`prepare_textures_lumine.bleed_colors()`。

**两个容易混淆的点**：

1. **这与"哪些材质需要 alpha 通道"是两件事**。本例只有 `skin` / `elem` 需要 alpha：
   实测 `颜.png` / `髪.png` / `衣.png` 的 alpha **全是 255**，即睫毛/眉毛/头发/衣服
   都是**几何成形**的，用 BC1 就够（不必为它们付 BC3 的体积）。
2. **判据必须逐面片取**：`diag_alpha_faces.py` 对每个面片取**该材质自己 UV 采样**
   的 alpha 均值。用**顶点级**统计会把"落在图集空白区的顶点"算成洞，
   得出"到处都是镂空"的错误结论。

**怎么证伪**：只看像素级 alpha 直方图是证不出来的（修前修后是同一个数）。
要把贴图**降采样到 mip 第 2–3 级再看遮罩边缘的 RGB**，深灰消失才算修好。

## §11.17 远处的头发/布料出现爬动的摩尔纹

**症状**：NPC 距离拉远后，头发、织纹、布料上出现细密**摩尔纹**；
NPC 一走动纹路**跟着爬**。近距离看不出。

**根因**：DDS **没有 mip 链**。GPU 只能点采样密集的发丝/织纹图集，
在任何"一个纹素小于一个像素"的距离上走样。自研编码器 `bc_encode.py`
原来硬写 `dwMipMapCount = 1`。

**先量（vanilla 对照）**：

```
char_ter_f_afr_blend_head_01_diffhq    2048²   mipCount = 12
其 -small 变体                          256²   mipCount = 9
```

即**每一张都有完整链**（2048² 的完整链是 12 级，256² 是 9 级）。

**修法**：BOX 降采样建金字塔，header 同时置位：

```
DDSD_MIPMAPCOUNT (0x20000)
DDSCAPS_COMPLEX | DDSCAPS_MIPMAP
```

**legacy DDS header 的字段偏移**（读错会静默生成错的链）：

```
flags@8    height@12    width@16    mipCount@28
```

读错 width/height 会让 1024² 看起来像 1024×2048，于是**多要一级 mip**。

**判据**：逐张 DDS 断言 `mipCount == floor(log2(max(w, h))) + 1`，
并检查 `DDSD_MIPMAPCOUNT` 标志位 —— 见 `06-verification.md` §10.1.2。

## §11.18 关节处断裂 / 台阶 / 缝隙（脚腕、肩臂、手肘）—— **已知问题，未解决**

**症状**：脚腕可见断裂/台阶、肩臂之间有缝、手肘处异常。静止时是"台阶"，
动画一播变成"撕裂"。

**度量口径（换了口径结论就完全不同）**：用**边长比 = 结果边长 / 全局拟合边长**，
**不要**用"边长 > N × 中位" —— 后者抓到的是模型本来就有的长结构边
（源长 9.3 cm 的边结果也是 9.3 cm，比值 1.0，却会被判成异常）。

```
40587 条边：拉伸比中位 1.000，99% 分位 1.966，比值 > 2.0 的 394 条
按部位分别统计：躯干 314 / 大腿 130 / 脚踝 28 / 肩颈 4
```

**根因**：源骨架的脊柱骨**几乎重叠**，X4 的是**分开的**。

```
源：下半身 与 上半身 只差 0.7 cm（MMD 把脊柱骨叠在腰上）
X4：Bip01 Spine 与 Bip01 Spine1 差 12.8 cm
```

逐骨各对各的目标，把源里几乎重合的两组顶点拉开 12.8 cm，
蒙皮在两者之间混合 → **跨越两者的边全被撕裂**。

**判据很硬**：394 条里 **72 条两端的主导骨是同一根**。刚体变换不可能改变距离，
所以这些拉伸只可能来自"位移不同的骨之间的混合"，不可能是单骨对齐错误。

**试过并且无效的**：

- **权重平滑**：4 / 10 / 20 / 40 轮结果**完全相同** ——
  两个相差 12.8 cm 的坐标系做混合，无论多平缓都会撕。
- **`blend_chain_offsets()`**（给一条链一份共享位移，与 `_harmonise_head_neck` /
  `_feet_share_one_offset` 同思路）：

  ```
  Spine 链（跨度 12.6 cm）：躯干 314 → 134              ✓
  腿链  （跨度 14.4 cm）：大腿 130 → 1，脚踝 28 → 0      ✓
  手臂链（跨度 18.8 cm）：手渲染成张开的爪子              ✗（平均后每根骨偏出近 10 cm）
  ```

  实机复测：**手臂和脚腕出现新的弯折，比它修掉的缝隙更显眼 → 全部回退**。

**当前取舍**：只保留 `fix_neck_source_weights`（局部、已验证归零，见 §11.19）。
撕裂的根源是"换骨架的固有代价"：两套骨架的脊柱/四肢比例差异客观存在，
真正干净的做法是**改骨架比例**，但那会破坏"骨架必须与 vanilla 逐字节相同"的硬规则。
**保留骨骼精确对齐，接受关节残余缝隙。**

**怎么证伪**：只有两件事算证据 —— ① 边长比口径下比值 `> 2.0` 的边数下降；
② 实机截图里缝隙变小且**没有引入新的弯折**。回退的理由正是第 ② 条不成立。

## §11.19 脖子中段有一个折角

**症状**：脖子上半段相对下半段向左歪，颈中形成折角。

**定位必须按源位置分层**：取源 z 的一个薄层（保证前后量的是同一批顶点），
再看该层在结果里的 x 中心。**按结果 z 分层会选到不同顶点集，数字不可比**
（曾因此误判一轮）。

```
源 z 148–151 层，源 x 中心 −0.01  →  修复前 +1.60，修复后 −0.00
```

**根因**：颈部下段的原始权重是 `上半身2` **58%** + `首` 42%。
MMD 里两者由同一套动画驱动，无所谓；重定向后：

```
上半身2 → Spine2   带 9.9° 拟合旋转
首     → Neck      只有 0.3°
颈部距 Spine2 枢轴约 26 cm；9.9° 在那个半径上 = 1.6 cm 的横向扫掠
而颈部上半段（100% 頭）纹丝不动 → 折角
```

**关键顺序教训**：第一次的修法在 stage1 里改**最终**权重 —— 它跑了、
移动了 674 个顶点、**折角一点没变**。因为顶点位置是在 `transform()`
**内部**用权重算出来的：等权重被改时，几何早就扫过去了。

**所以必须在 `transform()` 之前改源权重**：`fix_neck_source_weights()` ——
把颈部（`|x| < 7`、`z 145–157`）的 `上半身2` 权重转给 `首`。

**怎么证伪**：用同一条"源位置分层"口径在修复前后各量一次该层的 x 中心
（+1.60 → −0.00）。换一种分层口径量出来的数字**不能**作为证据。

## §11.20 飘带 / 链条被整体抬到不该在的高度

**症状**：飘带、链条、挂饰被整体平移到明显不对的高度（本例：全部被抬到头顶以上），
形状与长度正常 —— 是**整段位移**，不是形变。因为不改形状，
容易被误判成"贴图/材质问题"。

**根因**：**一个 X4 骨只能有一个直接驱动者**。两个源骨写同一个目标骨时，
谁赢取决于**字典遍历顺序**，既不报错也不是"后写的赢"。

本例第一版把 `上半身3` 和 `上半身2` 都映射到 `Spine2`：

```
上半身3（位置更低）赢了 → Spine2 的源位置变成 119.0 而非 ~132
绑在 Spine2 上的顶点被向上平移 13.9 cm
两条飘带的整条 19 节骨链正是折叠到 Spine2 的 → 飘带被从肩部抬到头顶以上
```

**判据**：`_assert_unique_targets()` —— 映射表构建完成后断言
**每个 X4 目标骨只被一个源骨驱动**，违反就报错并打印两个源骨的名字。
这个断言要在**映射表完成之后、`transform()` 之前**跑。

**修法**：把 `上半身3` 折叠到它的父骨 `上半身`（→ `Spine1`），而不是折到 `Spine2`：

```
飘带 z 范围  [55.9, 163.9]  →  [51.6, 156.5]        （Head z = 161.4）
```

修复后飘带上端低于 Head，回到肩部高度。

**怎么证伪**：量**折叠骨链**（飘带/链条/裙摆）的 z 范围与 Head 的 z 的关系 ——
飘带上端高于 Head 就是错的。不要从形状或材质入手，先量整段骨链的位移。
