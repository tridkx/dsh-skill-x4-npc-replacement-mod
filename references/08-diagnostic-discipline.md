# §12 诊断纪律：**尺子本身要先被证伪**

> 这一节来自第三个项目（原神荧 → X4 Terran 女性）的复盘。该项目里**每一个**
> "看起来是 mod 的问题"，最后都追溯到**诊断工具本身**。用户每次都对，工具每次
> 都在骗人。这不是运气问题，是可复现的失效模式。

## §12.1 为什么单列一节

前两个项目也有诊断脚本出错（`SKILL.md` 的"动手顺序"第 8 条已经提过一句），但代价可控。
第三个项目（荧）里它变成了**主要的时间开销**：同一个"衣服上有黑条纹"的反馈，
用户提了三次，本例三次用有缺陷的工具"证明" mod 没问题。

事后看，**每一次都是同一个错误的变体**：

> 用一个自己写的、与被测对象行为不一致的工具，去证明被测对象是对的。

工具的"正常"输出，和产品的"正常"，是两件事。

## §12.2 三条铁律

### 铁律一：诊断脚本必须与构建管线**共享配置**，不能各写一份

**案例**：构建阶段有一个 `DROP_STEMS = {'hairspec'}`，丢弃一个 98% 透明的
近黑色叠加层。预览脚本直接读源 PMX，**自己没做这个过滤**，于是把那一层也画出来
—— 软渲染不做 alpha 混合，就画成了实心黑。用户看到的"金发上的黑条纹"，
在 mod 里**根本不存在**。

> 注意这只是"**预览假阳性**"。若构建阶段确实**没有**丢弃 `hairspec`，导出器会把它
> 写成不透明层，实机就是真的"金发变黑发" —— 两者现象相同、根因不同，
> 见 `04-materials-and-textures.md` §7.7.4。

**做法**：配置放在一个模块里，构建和诊断都 `import` 它。
发现诊断脚本里出现第二份"材质名 → 用途"的表、第二个坐标换算函数、
第二个"哪些骨要特殊处理"的列表时，**立刻合并**。

**自检**：`grep` 一下同一份常量在几个文件里出现。

### 铁律二：预览与实机走的不是同一条路时，预览的"正常"**不算数**

**案例**：贴图上下颠倒这个 bug 存在于导出的 .xac 里，而**软渲染预览用的是源 PMX
的 UV**（不经过 Blender 的 UV 空间，也不经过导出器的 `1-v`）。所以预览永远是
正确的，只有实机才乱。同理，导出器把每个材质都写成 `blendmode="NONE"` ——
预览用自己的渲染器，看不到这件事，而实机里黑丝是不透明的。

**做法**：明确写下"这条预览链路经过了哪些环节"，并问**实机经过的环节是否都被覆盖**。
导出器 / 打包器 / 引擎材质解析 —— 这三个环节最容易被预览绕过。

### 铁律三：度量口径要先被证伪，**不要先信它**

**案例（最有代表性）**：为了量"关节有没有被撕裂"，本例用了
"边长超过网格中位 6 倍" —— 看起来很合理。它报了 313 条。

但把那些边打出来看：**源长度 9.31 cm，结果长度 9.30 cm，两端权重还完全相同**。
那是这个模型本来就有的长结构边（跨部件连接），**根本没被拉伸**。
正确的度量是**边长比（结果 / 全局拟合后的长度）**：中位 1.000，
> 2.0 的 394 条 —— 分布完全不同。

**做法**：任何"异常判据"先在一份**已知正常**的产物上跑（比如 vanilla 资产、
源模型、上一版成品）。**如果它也报异常，那是尺子的问题。**

## §12.3 实际发生过的失效清单（都可以当检查项）

| 失效 | 表现 | 根因 |
|---|---|---|
| 配置不同步 | 预览里金发有黑条纹，mod 里没有 | 诊断脚本没 import 构建脚本的 `DROP_STEMS` |
| **深度写入顺序** | 白衣服上一道道黑条纹 | 深度写在了 alpha test **之前**；被剪裁的纹素仍占住深度，后面的几何填不进来，露出背景色。**GPU 是先测 alpha 再写深度的** |
| 背景当信号 | "该材质 100% 是暗像素" | 统计暗像素时没排除背景，而背景本身就是暗的 |
| 负索引 | "已丢弃的 hairspec 还在渲染" | `ib = -1`（未覆盖）被当成 Python 索引 `-1`，取到了**最后一个**材质 |
| 分层选错顶点集 | "折角修复无效" | 按**结果** z 分层，前后两次选到了不同的顶点；必须按**源**位置分层 |
| 判据抓错对象 | "313 条边被撕裂" | "边长 > N× 中位"抓的是模型的长结构边，不是拉伸 |
| 工具链未验证 | 贴图朝向"已核对" | 核对用的链路本身绕过了出问题的那一步 |
| **判据方向写反** | "所有网格都是平面着色" | 看的是 `mesh.loops[i].normal`，它在**平滑**着色下返回*顶点*法线（同一顶点所有 loop 相同 → "spread" = 0），在平面着色下返回*面*法线。脚本把 0 标成了"flat"，于是正确的结果被读成了 bug（见下） |
| **指标的好方向跟着几何密度走** | "mod 的法线比 vanilla 更平" | `mean|dot(面法线, 顶点法线)|` 越高 = 相邻面夹角越小 = **网格越密**，不是越平；网格密一倍，同一个"平滑"会拿到更高的数 |
| **路径层级数错** | `FileNotFoundError` 指向 `proj\x4-character-retarget\...` | 从 `__file__` 推项目根时少写了一层 `dirname`；批量替换硬编码路径之后**要立刻跑一个会读这些路径的脚本**，别等到 Blender 阶段才暴露 |

### 判据写反的完整案例（最值得抄的一条）

法线自检脚本（当时叫 `diag_normals.py`，本 skill 统一称 `dbg_normals.py`）
打印过这么一行（继承自上一个项目）：

```
lumine_cloth_b   mean corner-normal spread 0.0000  (0 = flat, >0.2 = smooth transitions)
```

"全是平面着色"是两段式管线里最经典的错误（`from_pydata` 默认 flat，
导出器读的却是 `loop.normal`），于是按它去查了一轮。**实际是注释错了**：

```
mesh.loops[i].normal
    平滑着色 → 顶点法线（同一顶点的每个 loop 都取同一个值）→ 组内差异 = 0
    平面着色 → 面法线  （同一顶点的不同面各不相同）        → 组内差异 > 0
```

**0.0000 恰恰是平滑着色**。确认方式不是推理，而是**换一个尺度量同一件事**：
同一份产物在另一个工具里给出 `mean|dot(面法线, 顶点法线)| = 0.987`
（平面着色会是精确的 1.000），并与上一个已发布项目的产物**逐项对照**
（它同样是 0.0000 / 0.990）—— 两个项目、两个尺度、一个结论。

**教训**：

1. 一条判据的**文字说明**和它的**计算式**要分开审。说明是上一轮写的，计算式才是事实。
2. 报警先问"**它和已知正常的产物比过吗**"（铁律三）。这里"已知正常"就是上一个项目
   的成品：它报出同样的值 → 不是这一版的问题。
3. 修完把**判据文字**也改掉（`0 = SMOOTH`），否则下一个人还要查一遍。

## §12.4 一条可操作的自检清单

发版前，或"诊断结论与实机不符"时，逐条过：

1. **这个诊断脚本读的是哪份产物？** 是最新一次构建的吗（不是上一次的缓存）？
   > 实测踩过：改了 CORE 映射表之后没重跑 `diag_retarget`，于是用**旧坐标**
   > 分析了几轮。
2. **它用的配置和构建脚本是同一份吗？**
3. **它的链路覆盖了实机链路的所有环节吗？**（导出器 / 打包 / 引擎材质解析）
4. **它的判据在一份已知正常的产物上跑过吗？**（vanilla / 源模型 / 上一版）
5. **它选顶点/选像素的口径，前后两次一致吗？**（按源位置还是结果位置）
6. **它把"背景/未覆盖/空值"和"真实信号"区分开了吗？**（负索引、NaN、哨兵值）
7. **它是渲染出来的还是算出来的？** 涉及顺序（alpha / 深度 / 混合）的问题，
   只有渲染（而且是和引擎同顺序的渲染）能发现。
8. **结论能不能沉淀成一个可复现的判据？**（一张对照图、一条验证链、一个断言）
9. **判据的"文字说明"和它的"计算式"对得上吗？** 说明常常是上一轮写的、
   而计算式后来改过（或反过来）。**报警的方向**尤其要确认 —— 一条写反的注释
   能把"正确"读成"有问题"，把人送去修一个不存在的东西。

## §12.5 反向用法：把用户当判据

五次工程里，**用户的肉眼判断每次都对**，而诊断工具错了不止一次。
当用户说"这里不对"而工具说"这里对"时：

- **不要**先解释"那是模型自带的美术" —— 第三个项目里这样解释过两次，两次都错。
- **先**问清位置和形态（"上下颠倒还是左右错位"、"是断裂还是颜色不对"），
  然后**找一个不经过可疑环节的独立判据**去量同一个位置。
- 如果实在量不出来，**换一条链路**（比如换一个渲染器、从二进制直接读数据），
  而不是把同一个工具再跑一遍。
- 反过来也成立：**工具报警而图上看不出来时，先怀疑尺子**（甘雨那次
  "关节撕裂 1.87×"报警，逐张对比图确认无破面 —— 那个比值是宽袖长发这类
  **远离骨骼的服装几何**天然抬高的，工具没错，但**判据的适用性有边界**）。

> 用户能看见的，都是最终产物；工具能看见的，都是它自己那条链路。
> 两者不一致时，**错的多半是链路**。
