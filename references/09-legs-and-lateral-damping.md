# §13 腿、步态与横向阻尼（"猫步"这一类症状）

> 实测来源：荧（MMD/PMX，272 骨）→ X4 Terran 女性。
> 症状两轮才修好，第一轮方向对但量不够，**第二轮之前还发现游戏里装的是
> 三周前的旧版** —— 两件事都写在这里。

## §13.1 先做的一件事：把症状翻译成一个**可测的量**

"走路像猫步"这句话里已经藏着判据：**猫步 = 两只脚落在一条线上**，所以它度量的是
**两脚间距**，不是"某根骨偏离了多少"。

第一轮我修完报的是"脚踝骨与脚部几何的偏差从 7.06 cm 降到 2.47 cm"——那个指标
和猫步根本不是一回事，用户回"没用"。

| 症状原话 | 限定词给出的信息 | 要测的量 |
|---|---|---|
| "走动时是猫步，左脚放到右脚位置" | 静止正常、只在**动画**里出现 | 动画下的**两脚间距** |
| "坐姿两只脚贴得很近" | 与走路同源（都是横向宽度） | 同上 |
| "脚跟脚踝、小腿跟大腿，**动作完全不变形**" | 蒙皮/父子链/骨轴**都对** | 只剩横向位置 |

> **症状描述里的每个限定词都是判据**。"不变形"三个字一次排掉了蒙皮、父子链、
> 骨轴三大类原因；"只在走动时"排掉了绑定姿态类原因。这比二十轮离线测量有效。

## §13.2 硬规则：**横向阻尼必须整条腿用接近的折扣**

骨架比例不一致时（源腿内收、X4 外撇），逐骨对齐会把腿甩出去，所以要用横向阻尼
只保留一部分**横向**位移。**但折扣不能沿骨链逐级递减。**

实测（荧）：

```
目标值（逐级递减）   大腿 0.60  小腿 0.30  脚 0.20
→ 骨链横向位置       11.61 → 10.62 → 9.75 → 8.21     （折向内！）
→ 两脚间距           16.4 cm（几何 18.0）   vanilla 39.8
→ 脚踝骨 vs 脚部几何  7.06 cm 偏内
```

逐级递减不只是把腿**平移**，它把骨链**折弯**：每一节都比上一节更靠内，于是关节
落在它所驱动的几何内侧。绑定姿态截图看不出来（网格就是按这些目标生成的），
只有动画会暴露。

**正确做法**：

```
大腿 0.60  小腿 0.85  脚 0.95      → 10.62 → 13.72 → 17.11（单调外撇）
→ 两脚间距 35.9 cm（vanilla 39.8）
→ 脚踝骨 vs 脚部几何 0.28 cm
```

判据两条，缺一不可：

1. **骨链横向单调性**：大腿 < 小腿 < 脚踝（Biped 的腿是外撇的）。
   折向内就说明折扣递减了。
2. **两脚间距 ≈ vanilla**。这是"猫步"的直接度量。**只推到 vanilla 的 77%
   仍然看得出猫步**——第一轮我推到 30.5 cm 就被判"没用"，第二轮推到 35.9 cm 才过。
   **要跟 vanilla 比，不要跟"上一版"比。**

## §13.3 排错清单：动画不动的问题，按这个顺序量

每一条都能用数据判死，别靠渲染去猜：

| 检查 | 工具 | 合格判据 | 荧的结果 |
|---|---|---|---|
| 骨架与 vanilla 是否等同 | `xac.compare_skeletons` + 自己解析 .xac | **名称顺序、父子链、局部矩阵逐值相同**（旋转差 <1e-6 度） | 全部相同 |
| 左右是否镜像 | 逐骨局部坐标系的反射判据 | 每根骨 `R_right ≈ 镜像(R_left)` | 与 vanilla 同 |
| 权重是否挂到对侧 | 按主导骨统计顶点 x | `L` 骨的顶点在 +X（**先确认 +X 是哪侧**：X4 的 `left_eye_dummy` 在 +X） | 无跨侧 |
| 源数据自身是否健康 | 源骨位置 vs 它驱动的顶点中心 | < 1–2 cm | 0.69–0.97 cm |
| 脚骨旋转是否被跳过 | 实测 `NO_ROTATE_BONES` 跳掉的旋转量 | 大才需要在意的 | 0.0°（无需处理） |
| 骨链横向单调性 | 逐骨目标位置 | 单调外撇 | 见 §13.2 |
| **两脚间距** | 量成品资产（Blender 导入） | **≈ vanilla** | 35.9 / 39.8 |

> **别把"脚骨与几何的轴夹角"当判据**：荧是 30.4°，而 **vanilla 是 31.3°** ——
> 两侧一样，说明这就是 X4 脚部几何的常态（鞋子的长轴和踝→趾骨方向本来就不同）。
> 差 1° 的东西不值得动手；先量 vanilla 的同一个角，否则会把正常当异常修。

## §13.4 工具：量成品资产，而不是量中间数据

`b_*.npz` 这类中间 dump 只反映**上一轮构建**，拿它判断"修好了没"会骗人
（它在你重建之前就存在）。正确做法是 **Blender 导入刚导出的 .xac**，按顶点
主导骨分组，直接量：

```python
# tools/measure_legs.py 的思路
for ob in bpy.data.objects:            # 所有 mesh
    groups = {g.index: g.name for g in ob.vertex_groups}
    for v in ob.data.vertices:
        g = max(v.groups, key=lambda x: x.weight)      # 主导骨
        owner.setdefault(groups[g.group], []).append(mw @ v.co)
# 然后：每根腿骨的顶点 x 均值、两脚间距
```

判据值（本项目）：`两脚间距`（几何中心之差）、`每根骨 vs 它驱动的几何中心`。

## §13.5 验证纪律：**发版之后第一件事是核对游戏里装的是哪一版**

本项目最贵的流程漏洞：连做二十多轮离线诊断，**一次都没检查过游戏
`extensions/<id>/content.xml` 里的 `version`**。实际装着的是三周前的 v1.0，
从 v1.2 起的全部修复都没进过游戏，于是用户的"没用"其实是在描述初版。

```bash
# 每次"已修复"之后，先跑这个，再谈别的
grep -o 'version="[0-9]*"' "…/X4 Foundations/extensions/<mod_id>/content.xml"
ls -la "…/X4 Foundations/extensions/" | grep <mod_id>     # 有没有 backup/旧目录并存
```

三条配套做法：

1. **`content.xml` 的 `version` 跟着发布版本走**（`version="140"` = v1.4），
   这样用户和你都能在**扩展菜单里一眼看出**装的是哪一版；描述文字也别写坏
   （它会原样显示在扩展列表里）。
2. **部署 = 覆盖同一个 `<mod_id>` 目录**，别并存两个（同 id 会冲突）。
   覆盖前把旧的改名成 `<mod_id>.backup_<ver>` 是安全的，**但确认新版没问题后要删掉**。
3. 改完 mod 要**重启游戏**（X4 只在启动时读 extensions）。

## §13.6 顺序性陷阱（本项目实测）

```text
1. 看到"走路不对" → 先问"游戏里装的是哪一版"（§13.5），再动参数
2. 把症状翻译成可测的量（§13.1）——"猫步"= 两脚间距
3. 逐项证同（§13.3），别跳步：骨架/镜像/权重/源数据都在毫秒级可判
4. 改横向阻尼时按 §13.2：整腿接近的折扣 + 单调外撇
5. 重建 → 用 Blender 量**新导出的资产**（§13.4），跟 **vanilla** 比
6. 发版 → 覆盖安装 → 核对 version → 重启游戏 → 再看实机
```
